**commandant-bench 0.1.0**

commandant-bench is a review bench for [`commandant`](https://github.com/ModelArmy/commandant.cr) rulesets. It runs each rule against its examples and generated variants through the real engine, lints rulesets against the review guide, compares each rule's severity with similar rules across the corpus, and records reviewers' sign-offs, so a reviewer judges what a rule does rather than reading its JSON.

**Changes**

First release, for use by maintainers while the bench and the corpus are reworked together.

* **Bench API** - `Commandant::Bench::Workbench` reports on a rule or a whole ruleset: each example and generated variant is assessed by a fresh engine instance and judged ok, miss, false alarm or skipped, with the reason for every skip. Rule rows run against the file under review alone, so a platform-specific file cannot shadow it; engine rows run against the full tree. Results are JSON-serialisable for any presentation.
* **Variants** - Flag reordering, splitting and combining, quoting, an environment-variable prefix, an absolute binary path, `.exe` and `cmd.exe` for POSIX tools, and `sudo`, `sh -c` and compound wrappers. Each variant is tagged with the component a miss implicates: the rule, or the engine.
* **`report` and `try`** - Plain-text or `--json` reports for one rule or a ruleset, and ad hoc assessment of a single command on any platform.
* **`review`** - An interactive session that asks and scrolls: ruleset list, ruleset summary, rule cards with notes, lint, calibration and review state, a problems-only filter, `siblings` and `try`. Rendered with [Termify](https://github.com/nogginly/termify.cr) on a terminal, plain Markdown otherwise.
* **`lint`** - The review guide's mechanical checks plus checks only the bench can make, such as catch-all rules that fire on the bare command. Findings are errors or advice; `lint` exits 1 on errors.
* **Calibration** - Each rule's severity compared with rules sharing its risk tags, flagging outliers when close siblings agree on a different severity.
* **Sign-offs** - `signoff` in `review` records answers to the four review questions in a `reviews/` tree beside the rulesets, keyed by a hash of the rule, so editing a rule lapses its review. `status` lists each rule's review state.

**Known issues**

* Formats will change: `--json` output gains the unrecognised-flag check when the engine adds it, and rules gain an `examples` field when the corpus migrates. Adding `examples` changes a rule's hash, so sign-offs made before the migration will lapse.
* Until rulesets declare their flags, the `alias`, `long` and `abbrev` variants and the combination bench are skipped, and `reorder` assumes leading flags take no value: `usermod -o -u 0` becomes `usermod -u -o 0`. Every generated command is shown, so such variants are visible.
* The engine reports rules fired by the primary command only, so wrapper variants (`sudo`, `sh -c`, compounds) are judged by severity, not by which rule fired.
* Default rules have no examples yet, so their variants are not generated and lint does not require examples for them.
* Reports surface engine defects that are not yet fixed in `commandant`: `cmd.exe` flags are uppercased while Windows rulesets match lowercase, so no Windows rule fires; and an environment-variable prefix or an absolute binary path makes the tool unknown.
* A backtick inside a command is shown as `‵`, because Termify drops backticks within code spans.
* Linux builds need the `libxml2` development package for Termify's syntax highlighter.
* No binaries are published; build from source.
